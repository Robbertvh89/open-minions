# M6.4 scale re-run (NF-1, NF-2, NF-3): Apple M3 Pro

TASK-7.4.7. Re-run of the [M6.3 scenarios](m6-scale-apple-m3-pro.md) after TASK-7.4.2 to 7.4.6 and
7.4.8. Derived data: [`m6.4-scale-apple-m3-pro.json`](m6.4-scale-apple-m3-pro.json) (harness
`run` sections, `verify`, top `pg_stat_statements`, `docker stats`; no tokens, URLs or payloads).
Harness: `packages/minion-scale` ([report schema](scale-report-schema.md)). Run on 2026-10-18 at
`main` + commit `1cda843`.

## Configuration

- Mac: Apple M3 Pro, 12 cores; Docker VM 12 CPUs / 7.75 GiB. Compose project `open-minions-scale`
  with `deploy/compose.scale.yml`.
- Server: `MINION_SERVER_WORKERS=4`, pool 8 + 4 overflow per worker, `MINION_ACQUIRE_CONCURRENCY=8`
  per worker (overlay defaults). PostgreSQL 16: `shared_buffers` 1GB, `max_connections` 300.
- Load generator: `minion-scale run --procs 8` on the **same 12-core Mac** as server, Postgres and
  the other containers, so the sims compete with the server for CPU.
- Stress, knee, B, C, D use the overlay settings of M6.3 (sim heartbeat 5 s, watchdog timeout 20 s).
  A realistic uses the production ratio: heartbeat 300 s, watchdog timeout 900 s, first-acquire
  jitter 15 s, work 75 s (watchdog recreated with `MINION_HEARTBEAT_TIMEOUT_S=900` for that run only).

## Bottleneck: server CPU

During the 180 s stress rerun the server container ran at a median 388 % (max 409 %), i.e. all four
worker processes saturate four cores, while PostgreSQL ran at a median 94 % (about one of twelve
cores). B at 100k: server median 384 %, PostgreSQL 87 %. The limit at stress intensity is therefore
the server's Python processes, not the database. The load generator (8 procs) shares the same 12
cores. Not tested: more workers, or server and generator on separate hosts (config was fixed at 4
workers). Follow-up: TASK-36 (profile server CPU per acquire).

## Scenario C: watchdog

Host-side `minion_watchdog.main.tick` at DEBUG, timeout 20 s, batch 500, about 890k PENDING (n=1 per case).
Stale acquirements came from vanishing sims. The first 500-sim acquire burst was shed with 503 for
295 sims, so a top-up run (jitter 40 s) produced 705 stale in the first case, 500 in the others.

| Case | Stale reclaimed | Tick duration | Rounds | `over_lease_scan` scan_ms (hits) |
|---|---|---|---|---|
| with 0008 | 705 | 8,759 ms | 2 | 2, 1 (0) |
| with 0008, repeat | 500 | 9,313 ms | 2 | 3, 3 (0) |
| without 0008 (index dropped, recreated after) | 500 | 6,430 ms | 2 | 3, 1 (0) |

**Regression:** like with like, with migration 0008 the tick takes 8.8 to 9.3 s for 500 stale rows
against 1.7 to 2.4 s in M6.3; without 0008 it takes 6.4 s against 7.0 s (6,971 ms) in M6.3. Per row, with 0008, that is 12.4 to 18.6 ms wall
against 3.9 to 4.7 ms. `pg_stat_statements` for the 500-row repeat tick shows only about 0.4 s of DB execution
(attempt INSERT 0.19 ms, subtask UPDATE 0.17 ms, each x 500), so the time is per-row round trips from
the host through the Docker port forward, with more statements per reclaim now (settle, counter
select). It stays below the 20 s overlay timeout and the 900 s production timeout. Migration 0008
makes no measurable difference (the run without it was faster; M6.3 saw the opposite order, 7.0 s without vs 1.7 to 2.4 s with, so n=1 timings are not conclusive). Not investigated further:
follow-up TASK-35.

## Scenario D: rate limits

- Single burst (50 back-to-back acquires): 1 x 200, 49 x 429 (all `Retry-After: 1`), 429 latency 2.3 ms.
  DB work: one candidate query and one executor UPDATE for the admitted call; the 49 throttled calls
  ran only the token-lookup SELECT, no candidate scan, no write (NF-5 / ADR-0012 conform).
- Harness throttled (pace 0.05 s, 20 sims, 60 s): 17.1/s, 1,031 x 429, 1,033 admitted, candidate
  1,041 calls (1.01 per win), client acquire p99 <= 50 ms, 0 5xx.
- Harness control (pace 0.4 s, 20 sims, 60 s): 49.1/s, 0 x 429, 2,969 admitted, candidate 3,639 calls
  (1.23 per win; M6.3: 8.3 INSERT attempts per win), client p99 <= 250 ms.

## Caveats

- Client quantiles are bucket upper bounds, as are the server quantiles; "interp" values are linear
  interpolation inside the bucket.
- A stress, knee and D are not drained by design (time cap), so no NF-2/NF-3 check at 1M. NF-2 and
  NF-3 are verified at 100k (B). A 1M drain was not run.
- The first stress run had no `docker stats` sampler; CPU numbers come from the 180 s rerun and B.
- A realistic, knee, C and D ran sequentially on the same 1M DB after the first stress run; the
  stress rerun and B ran on freshly reset stacks (`down -v`).
- Realistic used hb 300 s: with 75 s work the sims send essentially only the ack heartbeat.
- Single runs, no repeats; run-to-run variance not measured.
- Load generator and server share one Mac; absolute numbers depend on that.
